MVMNT Phase 1 — data model & check-in security

Convened 27 July 2026, before the first migration. Required by App Spec §0 for data-model and security-sensitive decisions. 5 advisors · 5 anonymised peer reviews.

The question

Three decisions, pressure-tested before writing Phase 1 migrations for a run-club app (React Native/Expo + Supabase). ~300 people weekly, one event reached 2,500. Solo builder, UK/GDPR.

1. Schema shape — nullable timestamps instead of booleans, is_in as a GENERATED column, notifications split across two tables. 2. GPS geofence as the sole check-in factor, no QR — known to be spoofable, and check-ins become leaderboard points in Phase 2. 3. Nullable capacity with waitlist auto-promotion — what is concurrency-safe?

Where the council agrees

The generated column was the wrong thing to worry about

is_in as GENERATED … STORED buys nothing a partial index doesn't, and the expression is awkward to change later. Replaced with a view — same single source of truth, but free to redefine when Phase 2 changes what "in" means.

The real irreversible bug: a mutable single-row state machine

Three advisors reached this independently from different angles. Withdraw-then-rejoin overwrites history — and worse, if promotion touches signed_up_at, it overwrites the waitlist's own FIFO key and the queue silently reorders. Fix: an immutable queued_at, set once, never updated, plus an append-only event log beside the current-state row.

Store the check-in claim, not the verdict

Capture reported_lat/lng, accuracy_m, distance_m, client_ts, server_ts, method. Phase 2's leaderboard inherits Phase 1 data — you cannot re-adjudicate fraud you never recorded.

The notification split was right, but unsafe

Two tables is correct normalisation, not over-engineering — one event fans out to N devices. But with no idempotency key, a single cron retry double-pushes 2,500 people. Needs UNIQUE(run_id, type) on events and UNIQUE(event_id, token) on deliveries.

False negatives, not cheaters, are the live risk

Denied permission, phone in a locker, urban GPS drift. The admin manual check-in override is the highest-value and cheapest mitigation. GPS forensics is a solution to a problem nobody has had yet.

Where the council clashes

A club_id tenant key, now or never

The Expansionist argues this is the one column genuinely expensive to retrofit — it means rewriting every RLS policy and backfilling live data. That claim is technically correct. Four of five reviewers rejected it anyway as building for a company that doesn't exist.

Verdict: sided with the reviewers — but recorded as a deliberate deferral, not an oversight. If a second club is ever seriously proposed, that is the trigger to revisit, before there is production data rather than after.

Silent auto-check-in vs. a prompt

The Outsider was the only advisor to look at this as a member rather than an engineer: silent detection removes the receipt, and when it fails you find out via a wrong leaderboard and an argument with an organiser about something neither of you can see.

Verdict: sided with the Outsider. Geofence stays, but it prompts — "looks like you're here, check in?" — rather than deciding silently. Costs nothing, removes the most likely source of complaints.

Blind spots only peer review caught

Every advisor wanted more location data. None mentioned GDPR.

Four of five reviewers flagged it; zero of five advisors raised it. Lawful basis, retention window and an Article 17 erasure path have to be settled before the schema — an append-only log of location claims is precisely the thing that becomes hard to erase later.

The mass start breaks check-in operationally

Hundreds of simultaneous RPCs on congested mobile networks. Offline queue-and-sync with client_ts reconciliation is required, not optional — which makes the admin override load-bearing rather than a nicety.

Check-in has no check-out

Three advisors called it a "safety register." It cannot tell you who is still out on the route. Out of Phase 1 scope — but it doesn't do what the word implies.

Full advisor responses

The Contrarian strongest · 5/5

Decision 1 — the generated column is a distraction; the real bug is elsewhere. is_in STORED buys you nothing a partial index doesn't. Meanwhile it ships in every Realtime payload and PostgREST select, and you cannot readily alter a generated expression — only drop and re-add. Drop it.

The expensive mistake is nullable timestamps as a state machine. Withdraw-then-rejoin forces you to SET withdrawn_at = NULL, erasing history — and worse, it destroys waitlist ordering. What determines FIFO position: waitlisted_at or signed_up_at? If promotion sets signed_up_at = now(), you've overwritten your own queue key. Add an immutable queued_at set once at first join, never touched.

Second real bug: notification_events has no idempotency key. Without one, a single cron retry double-pushes 2,500 people. Also: push_tokens.expo_token UNIQUE requires ON CONFLICT … DO UPDATE SET user_id. Handed-down phones otherwise send someone else's notifications to the wrong account — a GDPR incident, not a bug.

Decision 2 — you're optimising against cheaters and ignoring false negatives: denied permission, indoor meeting points, urban drift. Build the admin manual override first; it's the only mitigation that matters.

Decision 3 — SELECT capacity FROM runs WHERE id = p_run FOR UPDATE at the top of the join and withdraw functions. Count-then-insert is unsafe under READ COMMITTED without it. Same lock, same order, both paths. Don't use a trigger.

The First Principles Thinker runner-up

You're asking "how do we stop GPS spoofing" when the actual question is "what is a check-in a record of?"

At a 300-person run everyone can see who turned up. Ground truth is social, not technical. In Phase 1 a check-in buys you a headcount and a safety register — spoofing that is worthless. Spoofing only becomes worth doing in Phase 2, when points exist. So don't build anti-fraud now; build evidence you can re-adjudicate later. Store the claim, not the verdict. When points arrive you can retroactively discount weak check-ins. That is the migration decision, not QR-vs-geofence.

The expensive irreversibility isn't is_in. It's UNIQUE(run_id, user_id) plus mutable nullable timestamps. Attendance is already an event log; you've written half of one and thrown away the half that matters. Keep the current-state row — it's right for 300 people — and add an append-only event table. Cheap now, unrecoverable later.

Two notification tables: not over-engineering — one event fans out to N devices; that's normalisation, not architecture.

Capacity: stop counting rows to decide. Serialising on the run row with FOR UPDATE is the simplest thing that is actually correct.

The Outsider 1 idea adopted

The auto check-in is the part that makes no sense to me. You're building a system where I arrive at a run and… nothing happens? No moment. Meanwhile the app silently decides whether I "counted." When it fails — phone in a locker, battery saver, GPS drifting 200m in a city — I have no idea until the leaderboard is wrong, and then I'm arguing with an organiser about a thing neither of us can see. A tap-to-check-in button is not friction. It's the receipt. Give them the automatic detection as a prompt, not as a verdict.

On cheating: you're solving it at the wrong layer. 300 people who see each other weekly already know who ran. The real anti-cheat is that Dave wasn't there and everyone noticed.

The waiting list will produce your first angry member. If a spot opens at 11pm and I'm auto-promoted, I wake up committed to a run I forgot I wanted. Do I lose the spot if I don't show? Is there a penalty? Auto-promote is a social contract, not a feature.

What you're assuming: that people sign up as individuals. They don't. They come with a friend, they bring someone new, they show up without signing up.

The Expansionist biggest blind spot · 4/5

The one column that isn't cheap later: club_id. "Add it later" is true for loyalty points. It is false for a tenant key, because retrofitting means rewriting every RLS policy and backfilling a live dataset. Put a nullable club_id on runs and profiles now and you've kept the option to be infrastructure for fifty clubs instead of an app for one.

Check-in is a spatiotemporal event and you're throwing away the payload. Store coords and accuracy. That seeds proof-of-attendance disputes, start-point heatmaps, and a proximity graph — who checked in within 30 seconds and 15 metres of whom — as a warm start for the QR friend system and a pre-filter for face-matching.

Your deliveries table already is the sponsor impression schema. Generalise it once and impressions, taps, pokes and check-ins all land in one pipe.

Unclaimed profiles. At 2,500 people most aren't in the app. Let admins check in a phone number that a real account claims later.

Reviewers' objection: this answers a Phase 1 scoping question with a Series A pitch, and treats a GDPR-governed location dataset as an asset to mine — proximity inference and biometric pre-filtering are special-category processing under Art. 9, and unclaimed profiles means creating records for people who never consented.

The Executor sequencing

Week 0, before any app code: supabase init + supabase start locally. Everything in supabase/migrations/*.sql, never the dashboard SQL editor. A seed script with 30 fake profiles and 5 runs — one starting in 10 minutes, one that ended yesterday, one at capacity with 3 waitlisted. You will run supabase db reset fifty times; if seeding isn't one command you will start avoiding tests.

Build order: schema + RLS → auth → run list/detail → sign-up/withdraw RPC → waitlist promotion → check-in RPC → admin editor → notifications last.

What eats days with nothing to show: RLS policies — budget 2–3 days and write assertion tests, because you cannot test RLS by clicking around. Also Expo prebuild + dev-client on two platforms: do it while the app is empty, not after 5,000 lines.

Fake without regret: push — write the events and a dispatch function that logs deliveries; the Expo call is 15 lines added later. Prove correctness by querying the deliveries table.

Where you get stuck: GPS. The simulator lies. Add a dev flag that lets you type coordinates, otherwise you're driving to a park to test one function.
